## What the levers demonstrably changed (observable, not inferred)

- **A works.** The original/A+B plans targeted only `newt-cli/src/crew.rs`. The A+B+C+D
  plans **include `update-…-display — Update newt-tui/src/lib.rs`** — the real seam.
  A's `[def]` hint pulled the correct crate into the plan.
- **B works.** The *original* run applied `<the full file content remains unchanged>`
  and produced a garbage branch. Runs 2–3 produced **no branch at all** — B refused the
  lazy emissions, so no garbage was delivered. "No branch" here is B doing its job.

## The definitive diagnosis (run 3 forensics) — build-speed was a red herring

Run 3 shared one **warm** `CARGO_TARGET_DIR` across the per-leaf worktrees (hardlink-clone
of the dev target; instant, ~0 disk) to test the "cold per-leaf builds are the bottleneck"
hypothesis. It **timed out at 90 min with no leaf landed.** The post-mortem:

- The crew **forked the first leaf's worktree** (`.newt/worktrees/crew-…`) — but it sat at
  **base: no edits, no commits.**
- **Every `target/` mtime predated the run** — nothing built after the clone. **The leaf
  never reached a `cargo build`.**
- devstral was responsive for small requests *after* the run, but **hung on the leaf's
  large prompt** (full-repo context).

**Conclusion: the per-leaf model call hung, with no timeout, and the entire run blocked on
it.** Build-speed was never the blocker — the leaf never built. The warm target is a real
efficiency win but is *not* the delivery cause. The 12-line `.plan.log` (vs ~85 min of
silence) is **block-buffered stdout lost on `timeout`'s SIGKILL** — so every run reads as
an opaque timeout.

For run 1 (Qwen), the model *did* progress (landed a leaf) but only a trivial `Cargo.lock`
edit in 60 min across 4 cold builds — slow + low code-quality, a different failure than
devstral's hang.

## The next bottleneck, named: crew per-leaf robustness (not grounding, not build-speed)

A/C fix grounding; B fixes delivery-correctness; D recovers from build-error mis-grounds.
**None of them bounds a leaf whose model call stalls.** That is the wall now:

1. **No per-leaf model-call timeout** → a hung/slow model (devstral on a large prompt) hangs
   the whole run until the outer `timeout` SIGKILLs it.
2. **Block-buffered per-leaf logging** → progress is invisible on a killed run, so the
   failure mode can't be diagnosed without forensics.
3. **C's recall is backtick-only** → it didn't refute the residual `help_lines`-in-`crew.rs`
   subtask because the model wrote the symbol unquoted.

## Follow-ups (to file + implement, then retest)

1. **Per-leaf model-call timeout + unbuffered progress logging (CRITICAL).** Bound each
   leaf's model call (and the leaf overall); on expiry, fail the leaf honestly (let D /
   triage act, or move on) instead of hanging. Line-buffer/flush per-leaf progress so a
   killed run is diagnosable. This is the enabler — without it every retest is an opaque
   60–90 min timeout.
2. **C symbol recall.** Broaden the claim-check's extraction (and A's grep terms) to catch
   **non-backticked** `snake_case`/`CamelCase` identifiers adjacent to def keywords ("the
   help_lines function"), not just backticked tokens.
3. **Warm-target verify (efficiency).** Have the crew's per-leaf worktrees share one warm
   `CARGO_TARGET_DIR` per run (scoped to the crew's **ephemeral** leaves — never the dev
   worktrees, per WORKSPACE_RULES). Not the delivery blocker, but cold per-leaf builds are
   pure waste once leaves actually run.

The honest bottom line: **the levers are sound and moved the observable behavior in the
right direction, but the crew cannot yet deliver a real multi-file issue end-to-end on
these local models** — and the reason is now precisely located (per-leaf execution
robustness), not guessed.
