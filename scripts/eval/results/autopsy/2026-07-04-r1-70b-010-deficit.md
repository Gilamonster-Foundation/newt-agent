## The biggest mover: worker-ignores-scope (9/9 classified)

worker-ignores-scope wins outright and unanimously — every classified item in this batch (all
confirmed genuinely FAIL) shows the same shape: a leaf gets a narrow, single-function instruction
and the worker either drifts into unrelated code (a fabricated `Bank`/`transfer` type, a
`maximum(a,b,c,d)` four-argument function instead of a slice-based helper), stalls mid-plan with
dangling worktrees, produces a helper with the wrong signature or wrong behavior, or reports a
false "nothing to land" on a leaf that actually changed the file. This is not one bad run — it is
r1-70b's dominant behavior on this case, reproduced independently across both candidate builds
(`candidate-3337921621` and `candidate-3818662010`).

The cleanest exemplar is `tmp.4nNfHaugIb`'s `extract-total` leaf, which was asked to extract a
single `total(nums: &[i32]) -> i32` helper and instead fabricated an entire unrelated banking type

## Next lever

**Fix worker-ignores-scope for r1-70b before trusting this model on multi-leaf plans.** The
argument:

1. **The rate is too high and too consistent to be noise.** 9/9 classified (10/10 including the
   unclassified-but-confirmed-FAIL `tmp.aOk1jan7XV`) across two independent candidate builds is not
   a fluke — it is the model's dominant, essentially unanimous behavior on this case. Any n≥5
   comparison sweep that includes deepseek-r1:70b on multi-leaf plans will be dominated by this
   mechanism unless it's addressed or the model is excluded from multi-leaf scoping until fixed.
2. **Three distinct failure shapes share one root cause.** Plan-abandonment (truncated `.plan.log`,
   dangling worktrees), scope drift (unrelated types/functions injected), and false "nothing to
   land" reports all trace back to the same underlying problem: the worker does not reliably confine
   itself to the leaf's declared instruction, and the plan runner has no recovery path when it
   doesn't. Fixing the confinement (tighter leaf-scoped prompts, or a scope-violation detector that
   fails the leaf loudly instead of drifting) is cheaper than chasing three separate symptoms.
3. **There is no grading-integrity lead here at all.** The one candidate grading-integrity claim in
   this batch didn't survive verification (see correction note above) — don't split effort chasing
   an oracle bug that isn't there.
4. **Respect the n lesson already logged for this line of work.** This is n=10 on one case with one
   model; don't generalize r1-70b's overall multi-leaf reliability past this candidate without a
   wider re-sweep, and don't compare it to other models' rates without re-running this same case
   against them under the same candidate build.

Concretely: before the next sweep that includes deepseek-r1:70b on multi-leaf plans, either (a) add
a scope-violation detector that fails a leaf loudly when its diff touches symbols outside the
declared instruction, or (b) tighten the leaf-authoring prompt specifically for this model family so
the instruction's boundary is harder to drift past, then re-run n≥5 to confirm the rate drops.
