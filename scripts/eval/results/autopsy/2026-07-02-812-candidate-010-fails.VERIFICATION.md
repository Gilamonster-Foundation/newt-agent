# Verification note on `2026-07-02-812-candidate-010-fails`

The autopsy's "grading-integrity" mechanism (6/12, cited as the top mover) does
**not hold up** — checked by hand, not accepted as-is.

## What was claimed

The autopsy report says six items were "logged as behavioral PASS, yet
re-running the case's own `tests/grade_spec.rs` ... fails" — i.e. a broken
grading oracle awarding false PASS verdicts, and recommends fixing the
harness before trusting any #812 re-sweep.

## What's actually true

Checked all three exemplars the report names (`tmp.B6ZQS32jTN`,
`tmp.4wLdVhoUpU`, `tmp.67nIMQXBXK`/`tmp.e1v6yFnHTm`) directly against
`scripts/eval/results/ab/812-worker-leaf-scope/candidate/sweep.tsv`: **every
one of them is recorded as `FAIL`**, not `PASS`. The claim that the sweep
mis-graded these as PASS is false on its face — it's checkable with one
`grep`, and the autopsy agents did not do that cross-check.

Then reproduced ratchet.sh's exact crew-mode grading procedure by hand on a
scratch copy of `tmp.B6ZQS32jTN` (checkout the last `crew/*` branch, drop in
the real `grade_spec.rs`, `cargo test --test grade_spec`): it fails with
**exactly** the three assertions the autopsy quoted
(`summarize_body_calls_only_the_helpers`, `summarize_delegates_to_all_three_helpers`,
`summarize_no_longer_computes_inline`) — same panic messages, same line
numbers. The grading pipeline worked *correctly* here: it detected a
genuinely broken decomposition (nested helper functions, a leftover `for`
loop, a stray `len()` call) and correctly failed it. There is no oracle bug.

The `target-grade-spec-inner` vs. crew-target mtime-ordering "stale build"
theory in the report is also not evidence of anything: `target-grade-spec-inner`
is a fresh throwaway dir created *during* grading (see
`newt-eval/cases/010-decompose-god-function/grade_spec.rs:225-241`, the
nested `cargo test --lib` recursion guard), so it necessarily postdates the
crew run's own build dir. That's the expected, correct ordering, not a
staleness symptom.

## What the evidence actually shows (the real finding)

Strip the wrong "mis-graded PASS" framing and what's left is genuinely
useful: on 3 of 4 models (devstral-small-2:24b, qwen3-coder:30b,
deepseek-r1:70b), when the candidate-#812 worker *does* land a final crew
branch (as opposed to the `worker-ignores-scope` group's abandoned/dangling
runs), the landed code is **structurally wrong** in ways the leaf-scope
fence has no power over — nested functions instead of siblings, computation
left inline instead of delegated, extra unauthorized calls in the
`summarize` body. The fence (#812) only gates *which files* a leaf can
touch; it says nothing about whether the code *inside* the touched file is
shaped correctly. That's a distinct, real failure mode from
`worker-ignores-scope` (wrong file) — call it `worker-lands-wrong-shape` —
and it's a strong argument that #836's landed extraction convention
(sibling-not-nested, no stray control flow) either isn't reaching this
model+task combination or isn't strong enough to close it.

## Recommendation

Do not act on "fix a broken grading oracle" — there isn't one, and chasing
it would be wasted work. The corrected next-lever hypothesis for #838:
strengthen the `CREW_PLAN_SYSTEM` extraction convention (or the per-leaf
verify feedback loop) to explicitly forbid the 3 concrete violations seen
here (nested `fn`, leftover inline loops, extra bare calls in the delegating
body) — the `worker-ignores-scope` findings' distinct `plan-run-abandoned`
symptom (truncated `.plan.log`, no completion line) is separately real and
worth its own look, but is not related to grading integrity either.
