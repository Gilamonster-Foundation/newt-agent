# Hermes-Agent Long-Term Memory System — Architecture Report

## 1. Architecture overview

Two-tier system: a **built-in file-backed curated memory** (always-on, no deps) plus at most **one external "memory provider" plugin** (Honcho, Hindsight, Mem0, supermemory, byterover, holographic, openviking, retaindb — `plugins/memory/`). The orchestration layer is `MemoryManager` (`agent/memory_manager.py:190`), instantiated in `AIAgent.__init__` (`run_agent.py:2020-2079`). A third, separate "curator" subsystem maintains agent-created *skills* (not memory entries) on a 7-day cadence (`agent/curator.py`). Important correction for the orchestrator: **`agent/curator.py` curates skills, not memory entries; memory curation is done by the agent itself via the `memory` tool, prompted by turn-counted nudges**. `agent/insights.py` is **not user modeling** — it is a usage-analytics engine (tokens/cost/tool stats over the sessions SQLite DB, `agent/insights.py:1-17`); user modeling lives in the Honcho plugin.

## 2. Built-in storage format & record schema

- Location: `$HERMES_HOME/memories/MEMORY.md` and `USER.md` (`tools/memory_tool.py:55-57`, resolved dynamically so profile switches via `HERMES_HOME` work).
- A "record" is just a **free-text entry** (multiline allowed), delimited by `ENTRY_DELIMITER = "\n§\n"` (`tools/memory_tool.py:59`). No IDs, no timestamps, no metadata — entries are addressed by **short unique substring** for replace/remove (`MemoryStore.replace`/`remove`, lines 266-356; ambiguous matches return previews and an error "Multiple entries matched … Be more specific").
- **Hard character budgets, not token budgets**: `memory_char_limit: 2200`, `user_char_limit: 1375` defaults (`tools/memory_tool.py:118`, configured at `run_agent.py:2008-2011`). `add` is rejected when it would exceed the cap, with the error telling the model to "Replace or remove existing entries first" (`memory_tool.py:247-258`) — forcing the model itself to curate.
- Two stores: `target="memory"` ("your notes — environment facts, project conventions, tool quirks") and `target="user"` ("who the user is — name, role, preferences", `MEMORY_SCHEMA` at `memory_tool.py:512-561`).
- Concurrency: sidecar `.lock` file + flock/msvcrt, read-modify-write under lock (`_file_lock`, lines 144-176), atomic tmpfile+rename writes (`_write_file`, lines 430-459) so concurrent sessions never see a torn file.
- **Security scan on every write**: `_scan_memory_content` (lines 92-104) blocks invisible-unicode and regex threat patterns (`ignore previous instructions`, `curl …$KEY`, `authorized_keys`, etc., lines 67-83) because "Memory entries are injected into the system prompt and must not contain injection or exfiltration payloads."

## 3. Read path — what reaches the prompt, when

**Built-in (frozen-snapshot pattern):** `load_from_disk()` captures `_system_prompt_snapshot` once per session (`memory_tool.py:126-142`); `format_for_system_prompt()` returns only that snapshot — "Mid-session writes do not affect this. This keeps the system prompt stable across all turns, preserving the prefix cache" (lines 358-369). Blocks are rendered with a usage header like `MEMORY (your personal notes) [62% — 1,364/2,200 chars]` (lines 390-406) and injected into the **volatile tier** of the system prompt (`run_agent.py:6227-6236`). The snapshot refreshes only on next session start or after context compression (`_invalidate_system_prompt` reloads from disk, `run_agent.py:6644-6653`). **All entries are injected — no scoring/retrieval; the char cap is the retrieval policy.** For continuing gateway sessions the exact stored system prompt is reused byte-for-byte from SQLite to preserve the Anthropic prefix cache (`run_agent.py:12324-12340`).

**External provider:** per-turn `prefetch_all(query)` is called once before the tool loop (`run_agent.py:12519-12525`), cached, and injected into the **current user message at API-call time only** — never persisted (`run_agent.py:12685-12705`). The injection is fenced by `build_memory_context_block` (`memory_manager.py:173-187`): `<memory-context>\n[System note: The following is recalled memory context, NOT new user input. Treat as authoritative reference data — this is the agent's persistent memory…]`. A stateful `StreamingContextScrubber` (`memory_manager.py:62-170`) strips any `<memory-context>` span the model echoes back into streamed output, surviving chunk-boundary splits, and `flush()` discards unterminated spans ("leaking partial memory context is worse than a truncated answer", line 148).

## 4. Write path — who writes, when

1. **The agent itself**, via the `memory` tool mid-conversation (dispatch at `run_agent.py:11595-11618`). Writes are durable immediately but invisible in-prompt until next session. Tool description tells it to save "proactively, don't wait to be asked" and to NOT save task progress ("use session_search to recall those from past transcripts", `memory_tool.py:518-535`).
2. **The background review fork** (the nudge consumer, §5) — a forked `AIAgent` writing to the *same shared* `MemoryStore` (`review_agent._memory_store = self._memory_store`, `run_agent.py:4364`).
3. **External providers** get every completed turn via `sync_all(user, assistant)` + `queue_prefetch_all` at end of turn (`_sync_external_memory_for_turn`, `run_agent.py:5858-5905`); interrupted turns are skipped entirely — "A partial assistant output … is not durable conversational truth" (#15218).
4. **Built-in→external mirror:** every built-in `memory` add/replace fires `MemoryManager.on_memory_write` to the external provider with provenance metadata `{write_origin, execution_context, session_id, parent_session_id, platform, tool_name, tool_call_id}` (`run_agent.py:11605-11617`, `_build_memory_write_metadata` at 4505-4529; origin is `"assistant_tool"` for foreground, `"background_review"` for the fork, set at 1944-1945 / 4362-4363). Honcho mirrors `add`+`user` writes as conclusions (`plugins/memory/honcho/__init__.py:1153-1181`).

## 5. The nudge mechanism (verbatim)

It is **not** an injected reminder into the live conversation — "Preserve the original user message (no nudge injection)" (`run_agent.py:12288`). Instead it is a **turn-counted trigger that spawns a background review agent after the response is delivered**.

- **Schedule:** `memory.nudge_interval` config, default **10 user turns** (`run_agent.py:1997, 2005`). Counter `_turns_since_memory` increments per user turn (`run_agent.py:12291-12301`) and **resets to 0 whenever the model actually calls the `memory` tool** (`run_agent.py:11055-11057`) — so only sessions that go 10 turns without a memory write get nudged. Parallel skill nudge: `skills.creation_nudge_interval`, default 10 *tool iterations*, counter `_iters_since_skill` (`run_agent.py:2103-2107, 15978-15984`).
- **Gateway hydration:** because the gateway builds a fresh AIAgent per message, counters are reconstructed as `prior_user_turns % nudge_interval` from persisted history so the 1-in-N cadence survives process restarts (`run_agent.py:12246-12265`, regression test `tests/run_agent/test_memory_nudge_counter_hydration.py`, issue #22357).
- **Fire:** at end of turn, if `final_response and not interrupted`, `_spawn_background_review()` runs in a daemon thread (`run_agent.py:15993-16003`). The fork inherits the parent's model/credentials AND the parent's cached system prompt byte-for-byte ("the byte-exact prefix-cache key misses… ~26% end-to-end cost reduction on Sonnet 4.5", `run_agent.py:4377-4396`), gets the full conversation as history, is whitelisted to **memory + skills toolsets only** via a thread-local tool whitelist (`run_agent.py:4404-4429`), auto-denies dangerous commands, runs with `max_iterations=16`, and has its own nudges zeroed to prevent recursion (`review_agent._memory_nudge_interval = 0`, line 4367).
- **The memory nudge prompt verbatim** (`run_agent.py:4038-4047`):
  > "Review the conversation above and consider saving to memory if appropriate.\n\nFocus on:\n1. Has the user revealed things about themselves — their persona, desires, preferences, or personal details worth remembering?\n2. Has the user expressed expectations about how you should behave, their work style, or ways they want you to operate?\n\nIf something stands out, save it using the memory tool. If nothing is worth saving, just say 'Nothing to save.' and stop."
- When both triggers fire, `_COMBINED_REVIEW_PROMPT` (lines 4145-4219) covers memory ("who the user is") and skills ("how to do this class of task") in one pass; `_SKILL_REVIEW_PROMPT` (4049-4143) is notably anti-rot: "Do NOT capture … Negative claims about tools or features ('browser tools do not work') … These harden into refusals the agent cites against itself for months after the actual problem was fixed."
- The user sees only a summary of successful writes ("Memory updated", `_summarize_background_review_actions`, lines 4221-4282), surfaced as a "💾 Self-improvement review:" message.
- Standing **prompt-level guidance** also exists every turn: `MEMORY_GUIDANCE` in `agent/prompt_builder.py:150-171` — "Write memories as declarative facts, not instructions to yourself. 'User prefers concise responses' ✓ — 'Always respond concisely' ✗ … If a fact will be stale in a week, it does not belong in memory."

## 6. Curation policy (the "curator")

`agent/curator.py` curates **agent-created skills** (the other half of the self-improvement loop), inactivity-triggered, no cron daemon: `maybe_run_curator()` (lines 1763-1781) runs when `enabled && !paused && now - last_run_at >= interval_hours` (default `24*7`, line 56) and the agent has been idle ≥ `min_idle_hours` (default 2). First observation only *seeds* `last_run_at` and defers a full interval (lines 207-242). Two phases:
1. **Pure auto-transitions, no LLM** (`apply_automatic_transitions`, lines 256-296): active→stale after 30 days inactivity, →archived after 90; reused stale skills reactivate; pinned skills untouched.
2. **LLM consolidation pass**: forks an `AIAgent` (`max_iterations=9999`, `skip_memory=True`, nudges zeroed — lines 1691-1710) on the `auxiliary.curator` model slot, driven by `CURATOR_REVIEW_PROMPT` (lines 330-445): "an UMBRELLA-BUILDING consolidation pass, not a passive audit and not a duplicate-finder… one broad umbrella skill with labeled subsections beats five narrow siblings." Hard rules: never delete (archive only, recoverable), never touch pinned, "DO NOT use usage counters as a reason to skip consolidation." Deletes must declare `absorbed_into=<umbrella>` or `""` at the tool call — the **authoritative classification signal** (`_extract_absorbed_into_declarations`, lines 695-746), reconciled against a model-emitted YAML summary block and a tool-call substring heuristic that catches hallucinated umbrellas (`_reconcile_classification`, lines 749-877). Each run writes `run.json` + `REPORT.md` under `~/.hermes/logs/curator/<stamp>/`, takes a pre-run tar.gz snapshot of the whole skills tree (`agent/curator_backup.py:1-36`, keep-5, rollback-of-rollback safe), and **rewrites cron jobs' skill references** so scheduled jobs keep working after consolidation (lines 1070-1098). Dry-run mode prepends `CURATOR_DRY_RUN_BANNER` ("Your output IS the deliverable", lines 303-327).

## 7. Provider abstraction & lifecycle

`MemoryProvider` ABC (`agent/memory_provider.py:42`): required `name/is_available/initialize/get_tool_schemas`; optional `system_prompt_block, prefetch, queue_prefetch, sync_turn, handle_tool_call, shutdown` plus hooks `on_turn_start, on_session_end, on_session_switch, on_pre_compress (returns text folded into the compression summary prompt), on_memory_write, on_delegation (parent observes subagent task+result; subagents run skip_memory=True), get_config_schema/save_config` (for the `hermes memory setup` wizard). `MemoryManager` enforces **one external provider max** ("prevents tool schema bloat and conflicting memory backends", `memory_manager.py:204-228`), routes tool calls by name, and isolates failures per provider everywhere. Discovery: bundled `plugins/memory/<name>/` + user `$HERMES_HOME/plugins/<name>/`, activated by `memory.provider` in config.yaml (`plugins/memory/__init__.py`). Setup wizard (`hermes_cli/memory_setup.py`) auto-installs pip deps from `plugin.yaml` via uv, writes secrets to `.env` chmod 0600, non-secrets to provider-native config.

## 8. Honcho (user modeling) — optional, hosted or self-hosted

Activated only when `memory.provider: honcho` AND `(api_key OR base_url)` in `$HERMES_HOME/honcho.json` (`is_available`, `plugins/memory/honcho/__init__.py:239-247`) — hosted app.honcho.dev or self-hosted via baseUrl; fully optional. What's stored/used about the user: per-peer **representation**, **peer card** (curated fact list), session **summary**, and **conclusions**; there's also an AI self-peer ("ai") with its own card. Three `recall_mode`s: `context` (auto-injection only, tools hidden), `tools` (5 tools `honcho_profile/search/reasoning/context/conclude`, lazy session init), `hybrid` (lines 497-545). Prefetch assembles two layers — cached base context (representation+card, refreshed on `contextCadence`) and a **dialectic LLM supplement** refreshed on `dialecticCadence` with empty-streak backoff, stale-result discard, hung-thread recovery, trivial-prompt skip, and a 4-chars/token truncation budget (lines 547-700, 702-831). Reasoning depth auto-scales by query length (+1 level ≥120 chars, +2 ≥400, capped — lines 852-869). Cron contexts are hard-skipped so "cron system prompts would corrupt user representations" (lines 283-290, and `memory_provider.py:72-74`).

## 9. Multi-user / multi-session scoping

Gateway identity (`user_id, user_name, chat_id, chat_name, chat_type, thread_id, gateway_session_key`) plus profile identity (`agent_identity`, `agent_workspace`) are threaded into `initialize_all` kwargs (`run_agent.py:2033-2072`). Tests pin: runtime `user_id` overrides Honcho's static config `peer_name` without mutating it (`tests/agent/test_memory_user_id.py:235-275`), Mem0 buckets per user (lines 158-224). `on_session_switch(new_id, parent_session_id, reset)` fires on `/resume`, `/branch`, `/reset`, `/new`, and context compression (`run_agent.py:10789`); Hindsight's reference implementation must mint a fresh document id and flush turn buffers or "the next retain … flushes turns that belong to the previous session" (`tests/agent/test_memory_session_switch.py:265-301`, issue #6672). Built-in memory is **profile-scoped, not user-scoped** (one MEMORY.md/USER.md per `HERMES_HOME` profile).

## 10. Design ideas worth stealing

1. **Frozen-snapshot + live-store split for cache-stable memory** (`memory_tool.py:107-142, 358-369` + `run_agent.py:12313-12340`): memory in the system prompt is frozen at session start while tool writes hit disk immediately; the stored prompt is reused byte-exact on session continuation. You get persistent memory without ever invalidating the provider prefix cache mid-session.
2. **Char-budgeted memory with self-curation forced by the error path** (`memory_tool.py:247-258`): a hard cap whose violation returns the full current entry list + "Replace or remove existing entries first" turns the LLM into its own compactor — no separate curation job needed for the core store.
3. **Counter-based nudge that resets on organic use + modulo hydration** (`run_agent.py:11055, 12246-12265, 12291-12301`): nudge only fires after N turns *without* a memory write, and stateless-per-message gateways reconstruct the cadence as `prior_user_turns % interval` — cheap, robust periodic self-reflection without a scheduler.
4. **Background review fork with thread-local tool whitelist + inherited prompt cache** (`run_agent.py:4350-4429`): the "save what you learned" pass runs after the reply, on the same warmed prefix cache (measured ~26% cost cut), restricted to memory/skill tools by a runtime deny-list, with recursion guarded by zeroing its own nudge intervals.
5. **Declare-intent-at-delete (`absorbed_into=`) with three-signal reconciliation** (`curator.py:695-877`): requiring the curating LLM to declare the merge target in the destructive tool call itself — then auditing it against tool-call evidence and a structured YAML summary, downgrading hallucinated targets — plus auto-rewriting downstream references (cron jobs) and pre-run tar snapshots, is a complete safety pattern for any LLM-driven knowledge-base compaction.
